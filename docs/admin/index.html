Technical notes

For whoever maintains the server. Nothing here is needed to use the connector — that is all on the main guide.

How it is deployed

A Python service on the same VPS as the stgconsulting.com site, behind its own nginx virtual host and its own TLS certificate. Nothing it does touches the existing site's configuration.

AI tool  ──HTTPS──▶  nginx                ──▶  127.0.0.1:8080  ──▶  Google APIs
                     mcp.stgconsulting.com      seo-analytics-mcp     Search Console
                     own cert, own vhost        systemd, user seomcp  GA4

One service account serves every teammate, so there is no per-user identity mapping and no OAuth to maintain. The unguessable path segment is the access control.

Why it is built this way

  • Its own user rather than www-data, so a file-read flaw in the Next.js site cannot reach the Google credential.
  • Its own certificate. Expanding the existing one would have re-issued the certificate the live site depends on.
  • No default_server — that stays with the main site, so a mistake here cannot capture its traffic.
  • Memory capped at 512 MB, so a runaway query kills this service rather than letting the OOM killer pick the larger Next.js process.
  • A service account rather than a personal token. The earlier personal OAuth token died after 55 days with invalid_grant, and only one person could have restored it.
  • uv-managed Python 3.13. The box ships 3.14, which has no grpcio wheels, so GA4 would have needed a source build.
  • Read-only by policy: in service-account mode the sitemap-submitting tool is unregistered rather than merely blocked.
  • Access tokens in SQLite, stored as SHA-256 only. The file can be copied off the box and grants nobody access, and revoking takes effect on the next request rather than needing a restart that disconnects everyone.
  • Sign-in fails closed. Configured without a domain allowlist, or without a public URL, it stays off and the server runs on hand-issued tokens rather than admitting every Google account in existence.
  • The token is read from x-api-key and several equivalent names, with or without a Bearer prefix. claude.ai allowlists header names on custom connectors and reserves Authorization for its own OAuth token, so a server insisting on one spelling is a server the client cannot be pointed at.

Runbook

Status and logs

systemctl status seo-analytics-mcp
sudo journalctl -u seo-analytics-mcp -n 50 --no-pager
curl -s https://mcp.stgconsulting.com/healthz

Restart

sudo systemctl restart seo-analytics-mcp

Update to the latest release

cd /opt/seo-analytics-mcp
sudo -u seomcp /usr/local/bin/uv pip install --python .venv/bin/python \
  --reinstall-package seo-analytics-mcp \
  "seo-analytics-mcp[http] @ git+https://github.com/zainsive/seo-analytics-mcp.git@main"
sudo systemctl restart seo-analytics-mcp

Who has signed in

Google sign-in is the normal way in; the hand-issued tokens below still work beside it, which is what let it be switched on without cutting anybody off.

cd /tmp
sudo -u seomcp SEO_MCP_TOKEN_DB=/opt/seo-analytics-mcp/state/tokens.db \
  /opt/seo-analytics-mcp/.venv/bin/seo-analytics-mcp people
# ... people --revoke someone@stgconsulting.com

Revoking ends their sessions immediately. They can sign in again unless the Google account or the domain allowlist also changes — for a leaver, disabling the Google account is what actually closes the door.

Issue and withdraw access

One token per person. Minting prints it once — only its hash is kept, so a lost token is replaced rather than recovered. No restart is needed for any of these.

cd /tmp     # the CLI cannot read the root-owned .env from elsewhere
sudo -u seomcp SEO_MCP_TOKEN_DB=/opt/seo-analytics-mcp/state/tokens.db \
  /opt/seo-analytics-mcp/.venv/bin/seo-analytics-mcp token mint alice
# ... token list      who has access, and when they last used it
# ... token revoke alice   effective on their next request

Pass SEO_MCP_TOKEN_DB explicitly as above. Run without it, the command writes to a different database and the server never sees the token — every command prints the file it used, so check that line. Add --days N to expire a token automatically.

The endpoint path

The endpoint is /mcp. It used to be a long random path, because before this server had any authentication that path was the only access control. It is not any more: every request needs either a Google sign-in or an issued token, and the service refuses to start without one.

The old path still resolves, through an nginx alias, so connectors added before the change keep working. That block can be deleted once nobody is using the long URL.

To remove someone’s access, revoke the person rather than changing the path — rotating a shared URL cuts off the whole team to remove one of them.

Settings

All in /opt/seo-analytics-mcp/.env. Restart after any change.

SettingPurpose
SEO_MCP_SERVICE_ACCOUNT_JSONThe Google credential, base64-encoded. Base64 because a private key's newlines defeat most .env parsers
SEO_MCP_ENDPOINT_PATHWhere the endpoint listens. /mcp. Not access control — the credential check is
SEO_MCP_ALLOWED_HOSTSPublic hostname. Without it every proxied request returns 421
SEO_MCP_PUBLIC_URLThis server’s own public address. Google sign-in builds its redirect URI from it, and it must match the Google console verbatim
GOOGLE_SSO_CLIENT_IDA Google OAuth Web application client. Its redirect URI is <public url>/auth/google/callback
GOOGLE_SSO_CLIENT_SECRETThe secret for that client
GOOGLE_SSO_ALLOWED_DOMAINSWho may sign in. Checked against Google’s hosted-domain claim, not the text after the @
SEO_MCP_TOKEN_DBWhere per-person tokens live (/opt/seo-analytics-mcp/state/tokens.db). Must sit under a ReadWritePaths= directory, since the unit sets ProtectSystem=strict
SEO_MCP_TOKENSFallback only: label:token pairs in plaintext, needing a restart to change. Prefer token mint
MAILCHIMP_API_KEYEnables the Mailchimp tools. Its suffix (-us15) selects the data centre, so it must be pasted whole — the base URL is derived from it
GSC_DEFAULT_SITESo nobody has to name the property
GA4_DEFAULT_PROPERTYSame for GA4
SEO_MCP_EXPORTS0 — no CSVs on a server nobody can browse
SEO_MCP_HOMECache and state directory
SEO_MCP_LOG_LEVELWARNING; use INFO while debugging

nginx directives that matter

proxy_buffering offWith nginx's default buffering the connector connects and then hangs forever
proxy_read_timeout 3600sThe 60-second default drops a live session mid-conversation

For anything else, call auth_status. It reports the credential mode, which APIs answer, what they expose, and the next step.

Open items

The main site's certificate will not renew. A renewal test found that the stgconsulting.com certificate cannot renew, because www.stgconsulting.com resolves to AWS rather than this VPS and validation there returns 403. It expires 8 December 2026 and would fail quietly around the 30-day mark, first appearing as browser security warnings on the marketing site.

Either point the www DNS record at 50.62.183.237, or drop www from that certificate if it is deliberately served elsewhere. This predates the connector and surfaced only because deploying it ran the test.
